# Baton 项目规格说明（spec）

本文档是 Baton 整个项目的完成指导：要做什么、做到什么程度算完成、现在做到哪一步。实现方式见 `docs/design.md`；两者冲突时以本文档为准。

**状态标记**（每条用户故事都有）：

- **完成**：已实现，并有自动化测试或已通过手动验收清单。
- **待验证**：代码已写，但还没有自动化测试，或还没在真实环境里验证。
- **未做**：还没有实现。
- **暂缓**：明确推迟，写有触发条件，满足条件再做。
- **已取消**：2026-10-27 方向调整后不再需要（见「方向调整」），原文保留作记录，相关代码按改造顺序删除。

一条故事只有在有自动化测试或手动验收步骤之后，才能标为「完成」。

## 问题

我已经在为几家 AI 订阅付费：ChatGPT、Cursor，以及按量付费的 DeepSeek。它们各自是一个孤岛：

- 每个工具有自己的上下文和记忆。在一个工具里讨论出的结论，换到另一个工具就得重新解释一遍。
- 想让一个模型出方案、另一个模型写代码、再换一个模型审查，只能我自己在几个窗口之间复制粘贴，还得记住谁做了什么、改了哪些文件。
- 让模型互相直接接力又不放心：没有规则约束，就可能自己审自己、在同一个问题上来回打转，或者悄悄把额度花光。
- 很多「多 agent 平台」要求接入 API key，但我已经有订阅，不想再为同样的模型按量付费。

## 方案

Baton 是一个跑在我自己电脑上的个人 agent 工作台。Pi 是引擎，Cursor 的模型通过官方 Cursor Agent CLI 接入。

- **用订阅登录，不用 API key**：GPT 系模型通过 ChatGPT 登录使用；Cursor 订阅里的非 GPT 模型通过 Cursor CLI 使用；DeepSeek 是唯一用 API key 的例外。每个模型家族只有一条接入路线：GPT 不会在 Cursor 里重复出现，也不提供 Auto。
- **一个 agent = 角色 + 运行时 + 账号来源 + 具体模型**：Cursor 里的每个模型是独立的 agent，不笼统地叫「Cursor」。
- **共享一切**：所有 agent 读写同一个工作区里的同一批文件，共用同一份房间上下文、记忆、教训和规则，使用同一套工具。
- **两种线程**：
  - **对话线程**：选一个 agent 直接聊，随时换 agent 接着聊，新 agent 能接上前面的内容。这是日常使用的主要方式。
  - **接力线程**：一件需要验收的事，按「方案 → 实现 → 检查 → 完成」推进，由 Baton 按规则挑选每一棒的 agent，不让 agent 之间自由传球。
- **规则约束接力**：检查者不能和实现者属于同一模型家族；交接次数、退回次数、空转次数和额度都有上限；检查命令失败时不能判通过；关键节点停下来等我确认。
- **一切可见、可撤销**：每个 agent 启动时收到了什么都能查看；每次写文件前自动快照，可以看 diff、一键回滚。

### 方向调整（2026-10-27，经我确认）

上面「两种线程」「规则约束接力」和「一个 agent = 角色 + 运行时 + 账号来源 + 具体模型」是最初的设想。实际用下来，日常要的是像现有 agent 应用一样「打开就是对话框」，接力和 agent 卡片都不刚需，反而让「想用某个模型聊天」变得绕。调整为：

- **对话优先**：打开 Baton 直接是一个新对话的输入框，左边是历史对话。只有一种线程：对话。
- **直接选模型，没有 agent 卡片**：输入框旁边选模型，三个已登录账号的全部模型都能选，随时换。对话只记「账号 + 模型」。「一个家族一条路线」照旧，由模型列表过滤保证（US-7）。
- **权限是对话里的开关**：只读（默认）/ 每次问我 / 允许直接改，只对这个对话有效。
- **接力降级成对话里的一个动作**：「让另一个模型检查」——选一个模型只读地审查这个对话里的改动，先跑配置好的检查命令，结论贴回对话。保留的规则只有两条：默认推荐不同家族的模型来检查；检查命令失败时不能判通过。
- **统一管理页**：账号、模型、工作区、上下文与记忆、检查命令在同一套管理页面里。

2026-10-27 补充（经我确认）：API key 不再只限 DeepSeek，任何常见服务的 key 都能接入并自动装配模型（US-101），GPT 也可以通过 key 使用；「一个家族一条路线」只约束两个订阅（ChatGPT、Cursor），key 线路和它们重复的模型都保留，按账号区分。

继续保留：三条账号路线、共享的房间上下文 / 记忆 / 教训 / 规则、同一套工具与权限判断、审批、快照与回滚、检查命令、MCP 桥接、安全要求、统计、桌面版。

### 阶段

| 阶段 | 内容 | 完成标准 |
|---|---|---|
| **P1 本地可用** | 本地网页 + 本地服务，三条账号路线，对话优先（2026-10-27 前是对话线程和接力线程） | 见下方「P1 完成线」 |
| **P2 桌面应用** | 用 Electron 打包同一套服务和界面 | 双击 `.app` 就能用，不需要终端；关掉窗口时服务也停止；界面和网页版是同一套 |
| **P3 更多 agent** | 接入 Claude Code、Gemini CLI、Codex CLI 等 | 第一个新 agent 接入时，不需要改路由、编排和界面主体；同一模型家族的路线可以在设置里切换 |

按 P1 → P2 → P3 顺序推进，前一阶段达到完成标准后才开始下一阶段。

例外（2026-10-26，经我确认）：P1 完成线里需要真实账号的第 1、2、3、5 条推迟验收，先开始 P2。P1 在这几条补完之前仍不算完成，P3 也要等它们补完再开始。

**P1 完成线**（全部满足才算 P1 完成）：

1. 三条账号路线都用真实账号登录成功：ChatGPT 登录、DeepSeek key、Cursor CLI 登录。
2. 对话：在一个对话里先后和三条路线上的模型各聊至少一轮。换模型后，新模型能正确引用前面讨论的内容；对话里记下的记忆，在另一个对话里能被检索到。
3. 改动与检查（2026-10-27 方向调整后替代原来的接力线程）：用真实账号，在任意一个目录里的一个对话中打开写权限，让一个模型完成一处改动 → 「让另一个模型检查」选一个不同家族的模型 → 检查命令通过、审查结论贴回对话 → 查看 diff，必要时回滚。整个过程不需要手动改 `.baton/` 里的任何文件。任务内容不限，写文档、整理资料都可以。
4. 自动化测试全部通过，GitHub Actions 在每次推送时运行并通过。
5. 「测试决策」里的手动验收清单全部通过。

## 实现决策

- **模块划分**（沿用现状）：
  - **核心引擎**：工作区存储、启动上下文拼装、记忆/交接/教训、工具注册表、权限、命令执行、影子 git 快照、补丁解析、检查、路由、执行器、编排。
  - **本地服务**：HTTP + WebSocket API、登录流程、凭据存储、审批转发。
  - **MCP 服务与 `baton` 命令行**：都通过本地服务的工具桥调用核心工具，不直接读写工作区状态。
  - **网页界面**：只通过 HTTP 和 WebSocket 与本地服务通信。这条是 P2 桌面版能直接复用界面的前提。
- **执行器**：Pi 执行器负责 ChatGPT、DeepSeek 和离线演示模型；ACP 执行器负责 Cursor Agent，以后也负责其他支持 ACP 的命令行 agent；演示执行器使用 Pi 的假模型。新增执行器时只需实现统一的执行器接口，并发出统一的运行事件。
- **路线规则**：模型家族由模型标识推导；每个账号来源只允许特定的运行时和服务商组合；P1 的路线是固定的。P3 时改成「每个家族一条生效路线，在设置里选择」，路线校验和模型列表过滤都按这个设置执行。
- **线程类型**（新增）：线程增加「类型」字段，取值为「接力」或「对话」。
  - 接力线程沿用现有的阶段状态机和路由。
  - 对话线程不经过路由和阶段状态机：我的每条消息触发一次运行，由我当前选中的 agent 执行。
  - 对话线程新增一个「对话」角色，对应一份角色规则：默认只读，可以使用上下文、记忆和读文件类工具，不提供挑选下一棒的工具。
  - 对话线程可以由我临时开放写权限，复用现有的「已批准权限级别」机制；写运行同样受「一个工作区同时只有一个写运行」约束，并且写之前快照。
  - 换 agent 时，新 agent 的启动上下文包含对话的滚动摘要和最近几轮原文，复用接力线程的「线程摘要 + 最近交接」机制。对话的每次运行也生成交接记录。
  - 发消息的 API 增加可选的「agent」参数，表示用哪个 agent 回复；新建线程的 API 增加「类型」参数。对话线程不要求验收标准。
  - 转成接力线程：新建一个接力线程，任务和验收标准由当前 agent 根据对话整理后交给我确认，两个线程互相保留链接。
- **方向调整后的实现（2026-10-27）**：上面「线程类型」一条里的接力部分和转接力不再保留。
  - 线程只有对话一种。线程记录当前选中的「账号 + 模型」和权限档位；运行记录照旧记运行时、模型和家族。
  - 执行器、启动上下文、工具和权限判断都不需要 agent 卡片：每次运行由「账号 + 模型 + 对话权限档位」临时生成运行身份。
  - 「让另一个模型检查」是对话里的一次只读运行，用「检查」角色规则；输入是这个对话里改动的 diff 和检查命令结果，输出结论贴回对话。
  - 旧的接力线程和 `.baton/agents/` 里的卡片不再读取，不做迁移（目前只有我一个用户，数据都是演示和验收用的）。
- **多项目（US-96，2026-10-27）**：本地服务为每个打开过的工作区各保留一个编排器，各自的写锁、快照、审批和整理员互不影响。「当前项目」只决定管理页显示哪个工作区、新对话默认开在哪；对话、审批、运行的接口按编号找到所属的工作区，不受当前项目影响。推送给界面的对话事件带上所属工作区。
- **硬规则的上限**：所有上限（交接次数、退回次数、空转次数、各账号额度、启动上下文预算、审批超时）都可以在设置里调整。默认值只写在代码的默认配置里，本文档不写具体数值。
- **联网控制**：「联网」策略只作用于 agent 自带的联网工具，P1 中即 Cursor Agent 的联网请求。Baton 不给 Pi 里的 agent 提供联网工具；命令行里的联网归命令审批管。
- **凭据**：凭据只存在本机的 Baton 数据目录，文件权限 0600；服务启动时从环境中移除 `OPENAI_API_KEY`；agent 运行命令时的环境变量去掉所有疑似凭据的变量。
- **数据位置**：工作区状态在工作区的 `.baton/` 目录；全局数据（凭据、设备标识、最近工作区、演示工作区）在 `~/.baton`，可以用环境变量改到别处。
- **可测试性改造**（新增）：本地服务的状态对象需要能在测试里注入数据目录、工作区、Cursor 命令和执行器配置，使测试可以在进程内构造完整服务而不监听端口。

## 测试决策

- **好测试的标准**：只测外部行为，即 API 的输入输出、工作区里文件的变化、线程时间线和状态，不测内部函数怎么实现。重构内部实现时测试不应该需要改。
- **唯一主切面：本地 HTTP API**。测试在进程内直接调用服务的 API，不监听真实端口，从新建线程一路测到完成。这一层覆盖：
  - 对话、权限档位和「让另一个模型检查」；
  - 权限与审批；
  - 登录状态（用替身模拟登录结果）；
  - 安全要求：Host 校验、写操作必须带 `X-Baton` 请求头、任何响应里都不出现凭据。
- **外部依赖的替身**（沿用现有的两个）：Pi 的假模型代替 GPT 和 DeepSeek，模拟的 Cursor CLI 代替真实的 Cursor。每个测试用独立的临时工作区和临时数据目录。
- **保留的单元测试**：路由、权限路径判断、命令策略、补丁解析、模型家族、记忆查重、启动上下文拼装、检查结果分类等纯逻辑，保留现有单元测试，不再新增其他切面。
- **迁移**：HTTP API 切面已建好（`apps/server/test/`，辅助工具 `testServer()` 在进程内构造服务），新测试都写在这一层。编排层原有的端到端测试保留，以后逐步上移。
